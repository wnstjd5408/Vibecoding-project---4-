# staging → Production 출시 절차

이 문서는 staging에서 검증한 변경을 Production(`main`)으로 내보내는 순서와 기록 양식을 정한다. 요구사항과 승인 상태의 원본은 Linear 이슈(MEG-21, MEG-189, MEG-193, MEG-195)이며, 이 문서는 공개 가능한 절차 요약이다. 실제 프로젝트 주소·배포 ID·계정 정보는 적지 않고 내부 출시 기록에 둔다.

## 먼저 읽을 것

- **staging 전체를 main으로 올리지 않는다.** staging에는 평가 전용 코드가 있고, `staging → main` PR은 브랜치명 검사(`meg-<번호>-<설명>`)에서 실패한다. 출시할 변경만 이슈 브랜치로 골라 `main`에 PR을 올린다.
- **검증한 것과 올리는 것이 같은지 확인한다.** staging에서 검증한 소스와 main 후보의 차이를 기록하고, 차이가 있으면 해당 CI와 smoke를 다시 실행한다.
- **출시 결정은 사람이 한다.** AI는 PR을 만들고 근거를 정리할 뿐 승인·병합·출시 승인·강제 승격을 하지 않는다.
- **DB 변경이 있으면 앱보다 먼저 확인한다.** 마이그레이션은 사람이 적용한다(D-008). 앱 롤백은 DB와 환경변수를 되돌리지 않는다. 세부 순서는 DB 절을 따른다.
- **막히면 출시하지 않는다.** 아래 "출시 중단 조건" 중 하나라도 해당하면 멈추고 사람에게 알린다.

## 1. 환경과 경로

| 환경 | 브랜치 | 배포 경로 | 사람이 거치는 단계 |
|---|---|---|---|
| Production | `main` | Vercel Git 연동. 운영 도메인 승격 전 필수 검사 확인은 정책 v2에 따른다(수락 대기, 아래 "사람 결정 필요") | main PR 승인·병합, 출시 승인 기록 |
| staging | `staging` | 필수 검사 통과 후 Preview(브랜치 `staging`) | staging PR 승인·병합 |
| PR Preview | 이슈 브랜치 | Vercel Preview | 리뷰어 확인 |

환경 구성과 환경변수는 [배포 가이드](deployment-guide.md), 검사와 워크플로는 [GitHub Actions 문서](github-actions.md), 시스템 구조는 [아키텍처](architecture.md)를 따른다.

## 2. 출시 후보 선정

출시 후보는 "이번에 Production에 올릴 이슈 목록 + 각 이슈의 main PR"이다. 순서는 다음과 같다.

1. **대상 이슈를 정한다.** 출시할 구현 이슈를 사람이 고른다. 이슈마다 AC, staging 검증 근거(검증 날짜·SHA·결과 링크), 미검증 항목을 한 줄로 적는다.
2. **변경 목록을 만든다.** 이슈별 PR과 커밋을 모은다. 평가 전용 변경이 섞이지 않았는지 확인한다.

   ```bash
   git fetch origin
   git diff --name-only origin/main...origin/staging   # staging에만 있는 파일
   git log --oneline origin/main..<이슈 브랜치>          # 후보에 들어가는 커밋
   ```

3. **미포함 항목을 기록한다.** staging에만 있고 이번에 올리지 않는 변경(평가 코드, 검증 중인 이슈)을 목록으로 남긴다. 이유 없이 빠진 항목이 없어야 한다.
4. **차이를 판정한다.** staging에서 검증한 SHA와 main PR의 최종 SHA를 비교한다.
   - 같은 변경이면 staging 검증 근거를 그대로 연결한다.
   - 충돌 해결·리베이스·선별 반영으로 코드가 달라졌으면 달라진 범위를 적고, 영향받는 CI와 smoke를 다시 실행한다.
5. **CI 근거를 연결한다.** 최종 후보 SHA의 `Product CI` 실행 링크와 결과를 기록한다. PR 실행 결과와 병합 후 `main` push 실행 결과는 SHA가 다를 수 있으므로 구분해서 적는다.
6. **DB 변경을 확인한다.** 후보에 `supabase/migrations/` 변경이 있으면 Production 적용 여부와 순서를 사람과 정한다(DB 절).
7. **사람이 출시를 결정한다.** 아래 승인 기록을 작성하고, 사람이 main PR을 승인·병합한다.
8. **출시 후 staging을 맞춘다.** 병합 뒤 `main` 변경을 staging에 반영해 두 브랜치가 어긋나지 않게 한다. 반영 방법은 기존 "staging에 main 반영" 이슈 방식을 따른다.

## 3. 기록 양식

출시 기록은 MEG-21 하위 이슈나 해당 릴리스 이슈의 댓글로 남긴다. 공개 PR에는 비밀값·내부 주소·고객 원문을 쓰지 않는다.

### 출시 후보 기록

| 항목 | 내용 |
|---|---|
| 대상 이슈 | 이슈 ID와 한 줄 설명 |
| main PR | PR 번호, 최종 SHA |
| staging 검증 | 검증 SHA, 날짜, 결과 링크, 미검증 항목 |
| 변경 차이 | 검증 SHA와 후보 SHA의 차이와 재검증 여부 |
| CI 근거 | `Product CI` 실행 링크, 결과, 실행 SHA |
| 미포함 변경 | staging에만 있는 평가 코드와 보류 이슈 |
| DB 변경 | 없음 / 있음(마이그레이션 파일명, 적용 담당, 적용 여부) |

### 출시 승인 기록

| 항목 | 내용 |
|---|---|
| 출시 승인자 | 사람 이름(AI 불가) |
| 승인 시점 | 날짜와 시각(KST) |
| 승인 대상 | 후보 SHA 또는 PR 번호 |
| 복구 후보 | 직전 정상 Production 배포 ID와 SHA. 앱만 되돌릴 때 DB·환경변수가 호환되는지 |
| 출시 중단 조건 | 아래 목록 중 이번 출시에 특히 볼 항목 |
| 결정 | 승인 / 보류 / 중단, 사유 |

main PR의 코드 리뷰 승인은 출시 승인과 다르다. 출시 승인 기록이 없으면 출시하지 않는다.

## 4. 출시 중단 조건

다음 중 하나라도 해당하면 출시를 멈추고 사람에게 알린다.

- 후보 SHA의 `Product CI`가 실패·취소·미실행이다.
- 후보 SHA와 staging 검증 SHA가 달라졌는데 차이를 기록하지 않았다.
- 평가 전용 코드나 승인받지 않은 변경이 후보에 포함돼 있다.
- DB 마이그레이션이 필요한데 Production 적용 여부·순서가 확정되지 않았다.
- 복구 후보(직전 정상 배포)를 확인하지 못했다.
- 출시 승인자가 정해지지 않았거나 승인 기록이 없다.
- staging 검증에서 실패나 이상이 확인됐고 원인이 풀리지 않았다.

## 5. 복구

- 기본은 사람이 판단하는 복구다. 자동 롤백, 자동 DB 롤백, 승인 없는 강제 승격은 쓰지 않는다.
- 앱 롤백은 이전 Vercel 배포를 다시 가리키는 것이다. 이미 적용된 DB 변경과 바뀐 환경변수는 되돌아가지 않는다.
- DB 변경이 있었다면 되돌리기보다 앞으로 고치는 방식(전진 수정)을 먼저 검토한다. 판단 기준은 DB 절에서 정한다.
- 직접 재배포나 강제 승격이 필요한 사고 대응은 사람이 사유·SHA·결과를 기록한 뒤에만 한다.

## 6. DB 변경 (MEG-195에서 작성)

이 절은 MEG-195에서 채운다. 그때까지 지켜야 할 최소 규칙은 다음과 같다.

- AI는 원격 Supabase에 쓰지 않는다. 마이그레이션은 PR 병합 뒤 사람이 적용한다(D-008).
- 후보에 마이그레이션이 있으면 출시 전에 staging과 Production의 적용 목록을 비교한다. Production에 빠진 마이그레이션이 있는 채로 앱이 먼저 올라가는 일이 없어야 한다.
- 적용 순서, 앱 이전·새 버전과 DB의 호환, 백업 확인, 복구 판단 기준은 MEG-195 PR에서 정한다.

## 7. 사람 결정 필요

아래는 제안이거나 수락 전인 항목이다. 결정되기 전에는 이 문서가 설정이나 동작을 바꾸지 않는다.

| 항목 | 현재 상태 | 결정할 사람 |
|---|---|---|
| Production 배포 경로(MEG-189 정책 v2: Git 빌드 후 필수 검사 성공 전 운영 도메인 승격 차단) | 정책 수락 대기(MEG-189 AC-3) | 김준성 |
| 별도 출시 승인 버튼을 두는지, main PR의 명시적 출시 승인 기록으로 갈음하는지 | 미결정 | 김준성 |
| 출시 승인 기록을 남기는 위치(PR 댓글 / 릴리스 이슈 댓글) | 제안: 릴리스 이슈 댓글 | 김준성 |
| 일반 PR Preview 유지 범위, 실패 알림 방식, 수동 재배포 권한 | MEG-189에서 별도 결정 | 김준성 |

## 8. 이 문서가 보장하지 않는 것

- 이 문서의 병합은 출시 승인이나 첫 릴리스 완료가 아니다. 첫 릴리스 완료는 MEG-21의 AC와 사람의 결과 수락으로 판단한다.
- 위 절차는 아직 실제 출시 후보로 시험하지 않았다. 첫 출시 후보로 기록 양식을 채워 보고 빠진 항목을 고친다.
- Production 도메인 승격 차단, 복구 시험, DB 호환 판정은 MEG-188·192·194·195의 결과를 따르며 이 문서에서 검증하지 않았다.
